## Usage Instructions

### When to Create Individual Feature Documentation

Create detailed feature documentation when:
- Impact score is 6 or higher
- Feature is complex (multiple components/integrations)
- Feature is frequently used
- Feature requires special configuration
- Feature has unique security considerations

### File Naming Convention

```
features/[feature-name-kebab-case].md
```

Examples:
- `features/user-authentication.md`
- `features/agent-marketplace.md`
- `features/real-time-collaboration.md`
- `features/payment-processing.md`

### Detection Logic

To identify features worthy of individual documentation:

1. **Scan for dedicated routes/pages**
   - Check `app/` or `pages/` directories
   - Look for route groups and nested routes

2. **Identify API endpoint groups**
   - Scan `app/api/` or `pages/api/`
   - Group related endpoints

3. **Analyze database schema**
   - Look for related table groups
   - Identify core entities

4. **Review component structure**
   - Find feature-specific component directories
   - Identify major UI sections

5. **Check configuration**
   - Look for feature flags
   - Find feature-specific env variables

### Content Guidelines

**DO**:
- Explain the "why" not just the "what"
- Include user perspective
- Document configuration steps
- Explain integration points
- Provide examples
- Keep security in mind

**DON'T**:
- Expose API keys or secrets
- Include sensitive credentials
- Document security vulnerabilities
- Reveal proprietary algorithms
- Include customer data
- Show internal security mechanisms

## Example: User Authentication Feature

```markdown
# User Authentication

> **Impact Score**: 9.4/10
> **Category**: Critical Core Feature
> **Status**: Active
> **Last Updated**: 2024-01-15

## Overview

User authentication system that handles user registration, login, session management, and OAuth integration. This is a critical feature that enables secure access to the platform and protects user data.

## Impact Classification

**User Adoption**: 100% of users (required for access)
**Business Value**: Critical (no platform without auth)
**Technical Complexity**: High (OAuth, JWT, RLS, sessions)
**Failure Impact**: Critical (application unusable)
**Development Effort**: Weeks of development

**Calculated Impact Score**: 9.4/10

## Purpose & Value

### Problem Solved
Users need a secure way to access their accounts and protect their data from unauthorized access.

### User Benefit
- Secure account access
- Multiple login options (email, OAuth)
- Persistent sessions
- Password recovery

### Business Value
- Enables user tracking and personalization
- Required for paid features
- Protects sensitive data
- Enables compliance (GDPR, etc.)

## Implementation

### Architecture
Built on Supabase Auth with custom middleware for route protection. Uses JWT tokens for session management and Row Level Security (RLS) for database-level authorization.

### Key Components
- **Auth Provider**: React context for auth state
- **Login/Signup Forms**: User-facing authentication UI
- **Middleware**: Route protection and session validation
- **RLS Policies**: Database-level access control

### Technology Stack
- **Frontend**: React, Next.js App Router
- **Backend**: Supabase Auth, Next.js API Routes
- **Database**: PostgreSQL with RLS
- **External Services**: Supabase Auth

### File Structure
```
app/
├── (auth)/
│   ├── login/page.tsx
│   ├── signup/page.tsx
│   └── layout.tsx
├── api/
│   └── auth/
│       ├── callback/route.ts
│       └── signout/route.ts
lib/
├── supabase/
│   ├── client.ts
│   └── server.ts
components/
└── auth/
    ├── SignupForm.tsx
    └── OAuthButton.tsx
middleware.ts
```

## Configuration

### Environment Variables
```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

### Dependencies
- @supabase/ssr - Supabase client for Next.js
- @supabase/supabase-js - Supabase JavaScript client

### Setup Steps
1. Configure Supabase project with auth providers
2. Set environment variables
3. Configure OAuth providers (Google, GitHub)
4. Set up RLS policies in database
5. Configure middleware for route protection

## API Endpoints

### POST /api/auth/signup
- **Purpose**: Create new user account
- **Authentication**: None (public)
- **Parameters**: email, password

### POST /api/auth/callback
- **Purpose**: Handle OAuth callbacks
- **Authentication**: OAuth flow
- **Parameters**: code, provider

### POST /api/auth/signout
- **Purpose**: End user session
- **Authentication**: Required
- **Parameters**: None

## Database Schema

### Tables/Collections
- **users**: Core user data (managed by Supabase Auth)
- **profiles**: Extended user profile information

### Relationships
- One-to-one relationship between users and profiles
- Foreign key constraints with cascade delete

## User Interface

### Pages/Routes
- `/login` - Email/password and OAuth login
- `/signup` - New user registration
- `/auth/callback` - OAuth callback handler

### Components
- **SignupForm** - Registration form with validation
- **OAuthButton** - Social login buttons
- **PasswordStrength** - Password strength indicator

### User Flows
1. User visits login page
2. Chooses email/password or OAuth
3. Completes authentication
4. Redirected to dashboard
5. Session persists across visits

## Integration Points

### Internal Dependencies
- **Dashboard**: Requires authentication
- **API Routes**: Protected by auth middleware
- **Database**: RLS policies enforce auth

### External Services
- **Supabase Auth**: Authentication provider
- **OAuth Providers**: Google, GitHub

## Security Considerations

### Authentication
- Password hashing handled by Supabase
- JWT tokens for session management
- Secure cookie storage

### Authorization
- Row Level Security (RLS) in database
- Middleware checks on protected routes
- API endpoint authentication

### Data Protection
- Passwords never stored in plain text
- Tokens encrypted in transit
- Session data secured

## Performance

### Optimization Strategies
- Server-side session validation
- Cached user data in context
- Optimistic UI updates

### Caching
- User session cached in React context
- Profile data cached with Next.js

### Scalability
- Stateless authentication with JWT
- Database-level authorization scales with Supabase

## Testing

### Test Coverage
- Unit tests for auth utilities
- Integration tests for auth flows
- E2E tests for login/signup

### Key Test Scenarios
1. Successful email/password login
2. OAuth flow completion
3. Session persistence
4. Password reset flow
5. Unauthorized access prevention

## Monitoring & Analytics

### Metrics Tracked
- Login success/failure rates
- OAuth provider usage
- Session duration
- Password reset requests

### Error Handling
- Failed login attempts logged
- OAuth errors captured
- Session expiry handled gracefully

## Known Limitations

- OAuth limited to configured providers
- Session timeout requires re-authentication
- Email verification required for new accounts

## Future Enhancements

- Multi-factor authentication (MFA)
- Biometric authentication
- Social login expansion
- Single Sign-On (SSO)

## Related Features

- **User Profile** - Extends auth with profile data
- **Dashboard** - Requires authentication
- **API Access** - Uses auth tokens
```
